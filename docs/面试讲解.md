# 面试讲解（云服务工单Agent）

## 一、3 分钟讲法

**背景（30 秒）**：云服务客服场景里，用户描述故障，需要查订单、查服务、查操作知识，最后可能建一张报障工单。
这个项目是一个本地可运行的 Agent 原型，把这条链路串起来。

**难点（40 秒）**：让大模型“能查但不能写”。查询是只读的、可以自动；建单有业务后果，必须人工确认。
同时要防止模型编造订单号、把示例编号当真实编号、在没检索时声称“根据知识库”。

**做法（60 秒）**：
1. 工具白名单只有 4 个只读工具（`suite/agent.py` 的 `TOOLS` / `read_tool`），模型没有建单工具。
2. 建单走任务状态机：草稿 → 核对 → 确认。`request_id` + 内容哈希做幂等，`version` 防止用旧草稿确认，
   `BEGIN IMMEDIATE` + `tickets.task_id` 唯一约束保证并发只出一张单。
3. 工具循环最多 4 轮，第 4 轮强制不再调工具，已拿到的结果降级成 `partial` 回答。
4. 会话用 `busy_until` 租约防并发覆盖，异常路径在 `finally` 释放。
5. 前端走 SSE（`status → tool → delta → done`），工具执行时就能看到进度。

**结果（30 秒）**：32 项 pytest（含 SSE 事件契约、并发确认、提示注入）、10 个离线场景评测、
前端按钮状态单元测试；demo 全离线可复现。

**边界（20 秒）**：业务数据是自编模拟，SQLite 单机，真实模型效果需要 `DASHSCOPE_API_KEY` 单独验证。

## 二、追问预案

| 问题 | 回答要点 | 代码位置 |
|---|---|---|
| 模型怎么选工具？ | TOOLS 里给 4 个 function schema；demo 用确定性路由，live 用 function calling，两者共用 `read_tool` 白名单 | `suite/agent.py` |
| 怎么防止编造订单号？ | 工具参数里的标识必须出现在本会话用户消息中（带边界正则）；无工具结果不得给业务结论 | `chat_events` 中 `identifier` 校验 |
| 怎么防重复建单？ | `UNIQUE(session_id, request_id)` + 内容哈希；确认时校验 `version` 与终态；`tickets.task_id` 唯一 | `draft` / `decide` |
| 两个请求同时确认？ | `BEGIN IMMEDIATE` 串行化写事务，第二个请求看到终态直接返回原工单 | `decide`，测试 `test_concurrent_confirm_one_ticket` |
| 模型一直要调工具？ | 固定 4 轮，最后一轮 `tool_choice=none`；不执行末轮新提议的工具，返回已有结果 + `partial=true` | `chat_events` |
| 流断了怎么办？ | 响应头已发出只能发 `error` 事件；会话租约 600 秒，`finally` 释放；生成器 close 也会释放 | `app.py` / `chat_events` |
| 会话太长？ | 超过 100 条把早期对话压成摘要，保留最近 60 条；摘要失败退回抽取式 | `_trim_history` |
| 为什么不用向量数据库？ | 知识资料就一个文档、几十个片段，SQLite 全量余弦是毫秒级；超过上限会显式报错 | `suite/rag.py` |
| 怎么做鉴权？ | `APP_TOKEN` 存在时写接口校验 `X-API-Key`（`hmac.compare_digest`）；页面右上角“访问口令”写入本机 localStorage | `require_token` / `ui.js` |
| 怎么接真实客服系统？ | `suite/tools.py` 的 `HttpTools`：超时 3/10 秒、5xx 重试一次、404 映射成“未找到”，业务层不改 | `tools.py` |

## 三、诚实边界（面试官会认可的部分）

- 引用只校验 ID 集合，**不校验语义支持**；文档和回复里都没有把它说成准确率。
- 业务数据是自编模拟，不是真实云厂商 API；`HttpTools` 是适配层示例，未对接生产。
- Docker / 云端验收在这一版没有复验，README 里如实标注，不冒充已完成。
